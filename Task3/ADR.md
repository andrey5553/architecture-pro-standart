### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**
Опишите здесь нефункциональные требования и архитектурно значимые требования.

| **№** | **Требование**                                                                                                                                                                   |
|:-----:|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|   1   | Время отклика системы не должно превышать 500 мс для пользовательских операций (просмотр депозитов, подача заявки). Загрузка справочных данных — не более 1 сек.                 |
|   2   | Система должна обеспечивать 99,9% uptime (не более ~(43 минуты х 12 месяцев) = 8,7 часов простоя в год). Интернет-банк и АБС должны быть доступны 24/7 (хотя часто в ночное время проводят регламентные работы).                                                     |
|   3   | Интернет-банк должен поддерживать горизонтальное масштабирование (добавление серверов под нагрузку). АБС может масштабироваться только вертикально.                              |
|   4   | При сбое в основном ЦОД система должна автоматически переключаться на резервный ЦОД с максимальным временем восстановления (RTO) ≤ 15 минут, но лучше всего иметь метрики сбоев и алерты на случай проблем в оборудовании.                                     |
|   5   | Все передаваемые данные (ФИО, номер телефона, реквизиты) должны шифроваться с использованием TLS 1.2+. Персональные данные в БД — AES-256. Обычно для перс данных заводят отдельный сервис, который их содержит, остальные носят лишь гуид или что-то подобное при передаче через сеть.                                        |
|   6   | Новые компоненты должны работать с Postgres и желательно перевести систему под эту СУБД. При необходимости внедрения Kafka/RabbitMQ — обеспечить совместимость после обновления интернет-банка.                                |
|   7   | Все критические операции (вход в систему, открытие депозита, изменение ставок) должны записываться в лог с возможностью аудита. Срок хранения логов — не менее 1 года.                           |
|   8   | Взаимодействие с АБС должно происходить через асинхронные очереди (Kafka/RabbitMQ) или буферизацию, чтобы избежать перегрузки. Прямые API-вызовы запрещены.                      |
|   9   | Время доставки SMS после подтверждения депозита — не более 30 сек. Отказоустойчивость SMS-шлюза — 99,5% uptime.                                                                  |
|  10   | Администраторы бэк-офиса должны иметь возможность загружать/обновлять ставки из XLS до полного перехода на АБС. Интерфейс должен поддерживать конфликт версий и откат изменений. |
|  11   | В рамках MVP — монолит, но с возможностью постепенного выделения сервисов (депозиты, кредиты, SMS, ставки). API должно быть RESTful + OpenAPI и плюс асинхронное взаимодействие.                                            |
|  12   | Справочники (списки депозитов, ставки) должны кешироваться на 5 минут для снижения нагрузки на АБС.                                                                              |
|  13   | Использовать c# (.net core) для backend, React/Angular для frontend. БД: Postgres (основная), Oracle (резерв).                                                                    |
|  14   | Система должна выдерживать ≥ 1000 RPS (запросов в секунду) в пиковые часы. Тестирование — c# + python.
|  15   | Все API, архитектурные решения и процессы должны быть описаны в Confluence/Swagger. Документация обновляется ежеквартально.                                                      |
